What is happening?

Core idea

TrainingRun starts from a snapshot of the current model. The terminal starts untrained by default; the desktop can start from a loaded checkpoint. The dataset consists of separate local story documents for training and validation. Batches use next-character targets shifted by one. Each update clears gradients, computes loss, backpropagates, clips gradients and updates parameters. The plotted train/validation losses use fixed windows so successive values are comparable. The orange validation curve does not receive optimizer updates.

Show it step by step

  1. Reset the shared model for a from-scratch comparison. Record the initial sample and loss.
  2. Choose 100 updates and start. Explain one update before discussing an epoch.
  3. Watch both curves. Pause with Stop; pending updates cease between steps.
  4. Compare greedy samples from the same prompt before and after.
  5. Save a run; load its after.pt in topic 005 or compare before.pt and after.pt in 008.
Change one thing

Terminal options: --steps, --learning-rate and --output-dir. With --step, the terminal pauses after each ten updates. In the UI, the learning rate is fixed when the run is created. Reset/reload before choosing a different learning rate; Start / continue adds updates to the existing optimizer. The implementation is in TrainingRun.advance(), measure() and save().

Questions to discuss

Can lower training loss mean memorization? Yes. Which data should choose settings? Validation. Why does training need more memory than inference? It also needs activations for differentiation, gradients and optimizer state.

Interpret the result carefully

These are tiny corpora and fixed diagnostic windows, not a broad language benchmark. Classroom save files are inference/comparison checkpoints; use llm_workshop.tiny for the longer resumable training workflow. Samples are collected at initialization, every 50 updates and final save.
